# Monk ships a minimal, Ractor-safe mailer, reversing "email stays outside the framework"

`docs/design/auth-sessions.md` decided that email delivery stays outside the framework: `Monk::Auth` hands the app a token, and the app brings its own mailer. That assumed a mailer the app could bring. It can't. Measured on Ruby 4.0.6 with `mail` 2.9.1, the current release and the engine under Action Mailer, `Mail.new` raises `Ractor::IsolationError` in any non-main Ractor: `Mail::Message#initialize` reads the class variable `@@default_charset`, and `Mail::Configuration` is a `Singleton` whose instance lives in a class-level ivar. Using the gem once in the main Ractor first does not help, because class variables are off-limits to non-main Ractors whatever they hold. The gem has 30 class-variable references across 6 files, so this is not a one-line patch either. Plain stdlib `Net::SMTP`, built per call inside the worker, works. So every Monk app that sends mail would end up hand-writing MIME and an SMTP or HTTPS client, which is the same argument that made Postgres a built-in rather than a bring-your-own.

We decided Monk ships `Monk::Mail`, opt-in through `require "monk/mail"`, with a deliberately small scope. A message is a frozen `Data` value with `from`, `to`, `subject`, `text`, `html` and `reply_to`, and Monk builds its MIME itself: plain text, HTML, or both as `multipart/alternative`, UTF-8 with base64 bodies and RFC 2047 headers. Attachments, inline images, BCC lists and bulk sending are out of scope. Delivery goes through a transport chosen by a single `MAIL_URL`, parsed and sealed at `Boot` through `freeze_hooks`: `smtp://` or `smtps://` for a local or remote relay, and `log://` for development. There are no provider-specific HTTPS transports: every transactional provider offers an SMTP relay, so a provider is just a `MAIL_URL` (examples in `docs/guides/mail.md`; the comparison, HTTPS APIs included, in `docs/mail-providers.md`). The cost is hosts that block outbound SMTP, which need a plan or host that allows it. Every transport builds its client fresh on each call inside the worker Ractor, the same pattern as `PG::Connection`. Monk takes on no runtime dependency: `net-smtp`, a bundled rather than default gem since Ruby 3.1, is declared by the app only if it uses SMTP, the same posture as `pg`, `redis` and `rqrcode`. An unset `MAIL_URL` means `log://` in development and a boot error elsewhere, matching `Monk::Auth.deliver_link`'s refusal to fail silently in production.

`Monk::Auth` keeps its `deliver:` hook unchanged, so an app is still free to deliver login links any other way; `Monk::Mail` becomes the default that hook is wired to, not a requirement. A send stays synchronous and blocks the worker Ractor for its duration, since Monk has no job queue. That cost is accepted and documented rather than solved here: a local relay (`smtp://localhost:25`) keeps it short.

## Considered Options

- Keep email outside the framework (rejected: the only mainstream Ruby mailer can't run where route handlers run, so "bring your own" means every app hand-writes MIME and an SMTP client, and gets header encoding and injection wrong on its own)
- Wrap or patch the `mail` gem (rejected: 30 class-variable references and a `Singleton` config would mean maintaining a fork, and it would add a heavy runtime dependency for the few features Monk needs)
- Run `mail` outside the worker Ractors, in the main Ractor or a separate process fed by messages (rejected: adds a queue and a process boundary to what is otherwise one synchronous call, for features that are out of scope anyway)
- Provider-specific HTTPS transports (`brevo://`, `lettermint://`, `resend://` ...) alongside SMTP (not taken for now: every provider already has an SMTP relay, so they would add code per provider for the one case of hosts that block outbound SMTP; `docs/mail-providers.md` has the comparison should that case matter)
- Generate the mailer into each app through `monk new --mail` (rejected: the code would be copied into every app instead of versioned and tested once, and fixes would never reach existing apps)
- Separate `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/... variables instead of `MAIL_URL` (rejected: one URL switches between SMTP and an HTTPS provider without code changes, and follows the precedent of `REDIS_URL` and Symfony Mailer's DSNs)
