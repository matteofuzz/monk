# Mail is sent from jobs with an explicit `deliver_later`, and a login link is created inside the job that sends it

ADR 0012 accepted that `Monk::Mail.deliver` blocks the worker Ractor serving the request, "since Monk has no job queue". `Monk::Jobs` (ADR 0013) removes that premise. We decided how mail and background jobs meet (`docs/history/plan-jobs.md` Phase 10).

**An explicit, opt-in `Monk::Mail.deliver_later`.** It takes exactly `deliver`'s arguments and enqueues a built-in `Monk::Mail::DeliveryJob`. It's loaded by its own `require "monk/mail/later"`, so `Monk::Mail` doesn't depend on `Monk::Jobs` or the reverse. `deliver` is unchanged. `deliver_later` accepts `wait:`, `at:` and `conn:` like any enqueue, so an email can commit or roll back with the app's own writes. It builds the message before enqueueing, without sending it, so bad input (`InvalidMessageError`) raises in the calling request exactly as `deliver` does, instead of failing later in the job process.

**HTML is rendered when enqueuing.** The caller passes `html: Monk::Mail.render(...)` as today, and the job stores finished Strings and only sends. Rendering costs microseconds (ADR 0010). The job process doesn't need the app's templates to send mail. A job enqueued before a deploy sends what was rendered then, rather than failing on a template the new release renamed. The HTML makes a wider payload row, which is cheap: the payload table is written once and deleted, never updated (ADR 0013).

**A login link is created inside the job that sends it, so the raw token is never stored.** `Monk::Auth` stores only token hashes, so that reading the database is never enough to log in as someone. Pointing the `deliver:` hook at `deliver_later` would store the complete link in `monk_job_payloads.args` until it's sent. That's a second or less normally, up to about 7 minutes of retries when the mail relay is down, and in a failed job until discarded, with the link valid for `login_ttl`. Instead, the app's login route applies its rate limit and checks `redirect_to`, then enqueues its own `SendLoginLink(email, redirect_to)`. That job calls `Monk::Auth.request_login`, builds the link and calls `Monk::Auth.deliver_link`, whose hook sends synchronously inside the job. The raw token exists only in the job's memory and in the email. As a side effect, `login_ttl` starts when the email is sent rather than when it was requested. A retry after a failed send creates a fresh token, and the unsent one expires unused. `monk new --auth --jobs` scaffolds this job. `Monk::Auth` is unchanged.

**Mail goes on a `mailers` queue, served first.** `DeliveryJob` and the scaffolded `SendLoginLink` use `queue "mailers"`, and the scaffold sets `JOBS_QUEUES=mailers,default`, so a backlog of other work never delays a login email. Once an app has long-running jobs, the guides recommend a dedicated `bin/jobs` for `mailers`. The `NOTIFY` wake-up skipped in ADR 0013 remains unnecessary for this.

**Only failures that retrying can fix are retried.** Jobs gain a general `never_retry *error_classes` setting: a listed error fails the job at once instead of spending its attempts. `DeliveryJob` doesn't retry a delivery the server refused for good (an SMTP 5xx or an authentication failure, recognized from the `DeliveryError`'s cause), but retries temporary failures (4xx, connection, TLS, timeouts) with the usual backoff. A job refused for bad credentials sits failed until `MAIL_URL` is fixed and `retry_failed` resends it. `SendLoginLink` has `max_attempts 3` (about 50 seconds of retries): a login email arriving minutes late, after the user has likely asked for another, is worse than a failed one.

## Considered Options

- **`deliver` itself enqueues whenever jobs are configured** (rejected: the same call behaves differently depending on another feature being loaded, its return value changes from the sent `Message` to a job id, and errors move silently from the call site to the job process)
- **No Monk API: each app writes its own mail job** (rejected: the same ten lines, and the same retry rules, copied into every app, which is what ADR 0012 rejected for the mailer itself)
- **Render in the job, from a template name and locals** (not taken: a second way to pass content, the job process has to load and freeze the app's views, and jobs enqueued during a deploy can reach a process that lacks their template; can still be added later)
- **The `deliver:` hook calls `deliver_later`, and the stored link is accepted** (rejected: it undoes, for up to `login_ttl` per request, the reason tokens are stored hashed)
- **Encrypt job arguments** (rejected: key handling and a crypto step in `Monk::Jobs` for what creating the token in the job avoids entirely)
- **Keep login links synchronous** (not taken, though safe: the login request waits for the SMTP send, and a relay that's down shows the user an error instead of being retried)
- **A high priority on the `default` queue instead of a `mailers` queue** (not taken: it has the same effect on backlogs, but mixes every job type on one priority scale, and is harder to split into its own process later)
- **Retry every `DeliveryError`** (not taken: a permanent rejection would fail four more times over about 7 minutes before ending up failed)
