# Monk ships an opt-in file storage layer: one S3-compatible backend for every provider, local files in development and test, and uploads that go from the browser straight to the bucket

Apps need somewhere to keep files users send (monk_talk: photos, voice notes, documents). In production that is always an external object store, and in development and test it should be the local disk. monk_talk will deploy on Hetzner and keep media in Hetzner Object Storage (`monk_talk/doc/v1-business-model.md` §3.2, `monk_talk/doc/staging-deployment-research.md` §5), but Monk must work the same with any S3-compatible service. Measured on Ruby 4.0.6 with rack 3.2.7, `Rack::Multipart.parse_multipart` can't run in a worker Ractor: it first fails on `Rack::Utils.@default_query_parser` (the bug `Base#parse_query_string` already works around), and sealing that at boot only moves the failure to `Parser::TEMPFILE_FACTORY`, then to a Proc in `Collector#on_mime_body`. Everything an S3 client needs does work there: `OpenSSL::HMAC`, `Digest`, `SecureRandom`, `Tempfile` and `Net::HTTP` over TLS. We decided the following on 2026-10-01.

**`Monk::Storage`, opt-in through `require "monk/storage"`, configured by one `STORAGE_URL`.** Same posture as `Monk::Mail` (ADR 0012): the URL is parsed and sealed at Boot through `freeze_hooks`, so a bad one fails the boot.

| `STORAGE_URL` | Backend |
|---|---|
| unset, in development or test | `file://storage/<env>` |
| `file://<dir>` | local disk, anywhere (an explicit choice, e.g. a server volume) |
| `s3://KEY:SECRET@bucket?endpoint=host&region=name[&path_style=1]` | any S3-compatible service: Hetzner, Cloudflare R2, Backblaze B2, AWS, MinIO, LocalStack |
| unset, in staging or production | boot error: on hosts whose disk is replaced on deploy, a silent fallback to local files would lose every upload |

**One S3-compatible backend, with SigV4 signing written in Monk.** Every object store an app is likely to use speaks the S3 API, the storage equivalent of "every mail provider has an SMTP relay". Monk names no provider in code: Hetzner is an `endpoint` and a `region`. Signing is about 150 lines with no gem dependency, the same reasoning as building MIME in ADR 0012 (`aws-sdk-s3` wasn't measured in a Ractor; it is a heavy dependency with global configuration, and Monk needs a handful of calls). Each backend is a frozen `Data` value holding only settings, and its HTTP client is built per call inside the Ractor doing the work, like SMTP and `PG::Connection`. A throwaway spike ran the whole flow below from a worker Ractor against LocalStack 4.3 with strict signature checking, and every check passed. `virtual-hosted` addressing (`bucket.host`) is the default, and `path_style=1` serves local servers.

**The API is small.** `put(key, io_or_string, content_type:)` (raw body, used by server code and jobs), `get`, `head`, `delete`, `copy`, `url(key, expires_in:, cache_window:)` (a signed download link), `presigned_put(key, content_type:, byte_size:, expires_in:)` (a signed upload link for a browser) and `generate_key(prefix:)`.

**Uploads go from the browser straight to the bucket, through a signed URL.** A route the app writes checks the session, the size limit and anything else the app cares about, then returns a `presigned_put` URL for `tmp/<key>`, valid for minutes, with `Content-Length` and `Content-Type` inside the signature. The browser PUTs the file there, and no worker Ractor is held while the bytes travel. Then the browser calls a confirm route: the app `head`s the object to check its size and type, `copy`s it from `tmp/` to its final prefix, `delete`s the `tmp/` copy and records it. The bucket isn't assumed to notify anyone (Hetzner doesn't support event notifications), so the confirm call is the only signal. A lifecycle rule expiring `tmp/` after a day removes uploads that were never confirmed, without a cleanup job. Monk doesn't parse `multipart/form-data`, so the Rack problem above never arises. An upload form without JavaScript isn't supported until an app needs one.

**Downloads go through a stable app URL that redirects to a signed link.** Pages, and Live patches in particular, contain `/media/:id`-style URLs the app routes. The route checks that the viewer may see the file, then redirects (302) to `url(key)`. A patch is rendered once and shared by every subscriber (ADR 0010), so it must not contain a link that expires or belongs to one viewer. `url` rounds the signing time down to `cache_window` (an hour by default) and signs for `expires_in` beyond it. Within the hour, every redirect then points at the same URL, and the browser's cache works. Buckets stay private. A public-bucket mode can be added later for content that is public anyway.

**The file backend behaves like a bucket, and in development and test Monk mounts its two routes.** `PUT /_monk/storage/:token` and `GET /_monk/storage/:token` stand in for signed URLs. The token is HMAC-signed and holds the key, the method, the expiry, and for uploads the length and content type, so the file backend refuses what the bucket would refuse, and a test catches the mistake before staging does. Its key is a fixed development value in development and test, so a link built by `bin/jobs` also works in the web process. In staging and production, `file://` requires a `STORAGE_SECRET`. Keys are checked against a strict character set and resolved inside the root directory, with the same containment check as `Assets#disk_entry`. Files are never stored under `public/`: the asset manifest is frozen at Boot, and in development `public/` is served from disk as trusted content.

**Monk stores bytes. The app keeps the records.** Keys come from `generate_key`, random and never derived from the user's filename, which rules out path traversal and keeps file names out of URLs. A key isn't the content's hash: a hash reveals when two users stored the same file, and deleting then needs reference counting. Filename, content type, size and checksum live in the app's own table. Monk ships no attachments table, no image processing and no multipart upload to S3 (a single PUT takes up to 5 GB on both AWS and Hetzner). It ships one helper that identifies a file's type from its first bytes (PNG, JPEG, GIF, WebP, Ogg/Opus, PDF), since the client's `Content-Type` can't be trusted. It also ships a rule refusing SVG, which can carry scripts, and the dev routes send `X-Content-Type-Options: nosniff`.

**Monk never proxies a download, so server-side encryption that needs the app on every read is out of scope.** Hetzner's only server-side encryption is SSE-C, where every read must carry the key, so a plain `<img src>` with a signed link can't work, and each download would hold a worker Ractor. monk_talk will encrypt media in the browser instead, from its first release with media. The bucket stores opaque bytes, and thumbnails and EXIF stripping happen in the browser before encrypting. That is an app decision, and Monk needs nothing for it.

**Two Hetzner facts apply to any deployment that uses it, and they belong in the guide, not in code.** An S3 key pair can access every bucket in its Hetzner project, so staging and production need separate projects. Hetzner doesn't replicate between locations and copies only within a bucket, so a backup copy is a job that downloads and uploads again (traffic inside Hetzner's eu-central network is free).

## Open items

These four were checked only against LocalStack. LocalStack imitates AWS, and Hetzner runs different software, so each must be checked on a real Hetzner bucket (a staging project) before the S3 backend ships. The spike that passed on LocalStack becomes an integration test run against a bucket given by environment variables. Each item notes what changes if it fails.

1. **Hetzner enforces a signed `Content-Length` on a presigned PUT** (a longer body or another content type is refused with 403). If it doesn't, the size limit is only applied at confirm, where an oversized `tmp/` object is deleted, and abuse is bounded by the one-day `tmp/` expiry. A presigned POST with `content-length-range` is the alternative, and Hetzner's support for it is unverified as well.
2. **A CORS rule allowing `PUT` from the app's origin is honoured**, and a preflight from another origin is refused. Hetzner documents CORS, but only with a GET/HEAD example. If PUT isn't allowed, uploads go through the app as a raw-body PUT streamed into `put`, which holds a worker Ractor for the upload.
3. **A lifecycle rule using `<Filter><Prefix>tmp/</Prefix></Filter>` with `Expiration` and `AbortIncompleteMultipartUpload` is accepted.** Hetzner's example uses the older top-level `<Prefix>`. If only that works, the guide uses it. If neither works on a prefix, unconfirmed uploads need a cleanup job.
4. **`x-amz-copy-source` copying within a bucket works, with region `fsn1` and both URL styles.** Hetzner lists same-bucket `CopyObject` as supported, and its curl examples put the bucket in the path. If copying fails, uploads go to their final key, the app records them as pending, and a job deletes pending ones that were never confirmed.

## Considered Options

- **Uploads through the app as `multipart/form-data`** (rejected for now: Rack's parser can't run in a worker Ractor, so Monk would need its own streaming parser, and each upload would hold a worker Ractor twice, from the client to the app and then to the bucket; a no-JavaScript form is the case that would bring it back)
- **Uploads through the app as a raw-body PUT** (kept for server-side code and jobs through `put`, not for browsers: it still holds a worker Ractor for the whole upload)
- **`aws-sdk-s3` or another gem** (not taken: not measured in a Ractor, heavy, with global configuration; the calls Monk needs fit in one signer, as with MIME in ADR 0012)
- **One adapter per provider (`hetzner://`, `r2://`, ...)** (rejected: every provider here speaks S3, and the differences are an endpoint, a region and an addressing style)
- **Separate `S3_ENDPOINT`/`S3_BUCKET`/... variables instead of `STORAGE_URL`** (rejected for the same reason as `MAIL_URL`: one value switches backend without code changes)
- **Signed URLs written directly into pages** (rejected: a Live patch is rendered once for every subscriber, and a link that expires or belongs to one viewer breaks Resync and sharing; per-request redirects keep the check on every view)
- **A fresh signature on every redirect** (rejected: each redirect gives a new URL, so the browser downloads the same image again every time)
- **Public buckets** (not taken now: monk_talk's media is private; a public mode can be added for avatars or other public files)
- **Keys derived from the content's hash** (rejected: reveals that two users stored the same file, needs reference counting to delete, and gains nothing once media is encrypted in the browser, since every upload's bytes differ)
- **Server-side encryption with SSE-C** (rejected: every read must carry the key, so the app would proxy every download)
- **An in-memory backend for tests** (rejected: it would need a `StateRactor` and would behave less like a bucket than the file backend with a temporary directory)
- **An attachments table and model in Monk, like Active Storage** (not taken: what an app records about a file is app-specific; `monk new --storage` can generate an example migration)
- **Image variants and thumbnails on the server** (not taken: they don't work once media is encrypted in the browser, and `ruby-vips` hasn't been measured in a Ractor; an app that needs them can do it in a job)
