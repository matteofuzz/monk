# A topic is an opaque name, so recipient and entity topics both work and access is denied by default

Two shapes of "who hears about a change" are natural here: a recipient topic (`contacts:7`, each user subscribes to their own channel and the publisher loops over whoever should be told) and an entity topic (`contact:42`, each client subscribes to every entity it displays and one publish reaches everyone watching). We decided against choosing between them in the framework: a topic is just a name mapped onto a `Registry` key (a Symbol, per `RedisFanout`'s constraint), both shapes run on that one primitive, and recipient topics are the documented default while entity topics get no special code. Recipient topics are the default because they fit deny-by-default authorization (a subscription policy of "you may listen to your own topic" needs no lookup) and because they are the only shape that supports per-viewer fragments; entity topics need an app policy that can answer "may this subject watch this entity?" per subscribe. Subscribing is denied unless an app-supplied policy (`Monk::Live.authorize("contacts:*") { |subject, topic| ... }`) allows it, since any authenticated connection could otherwise subscribe to any topic and read fragments rendered from data it may not see. The Phase 0 fan-out measurement adds a scaling reason: broadcast cost is per subscriber (about 100ms at 1,000 connections on one topic, and it blocks the single-threaded `Registry` for its duration), and recipient topics keep per-topic subscriber counts small.

## Considered Options

- Recipient topics only (rejected: forces an N-way publish loop even where one shared entity fragment would do, and rules out the cheap "everyone watching this contact" case)
- Entity topics only (rejected: a page with 200 contacts subscribes to 200 topics that change as friendships change, authorization becomes a per-topic lookup, and per-viewer fragments become impossible since everyone on a topic gets identical HTML)
- Allow-by-default with an optional policy (rejected: the failure mode is silent, and it is a data leak, not a bug)
