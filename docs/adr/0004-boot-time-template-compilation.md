# Templates compile at Boot, never at request time

Every other Ruby template engine — Tilt, ActionView, Sinatra's `erb` helper — compiles a template on first render and memoizes it. That design is unavailable here: the memo is shared mutable state, and the compiled artifact is a method installed on a module every Ractor sees, which a worker Ractor may not do. Where a Ruby version permits it anyway, parallel workers racing to redefine the same method is precisely the silent loss of safety ADR 0003 exists to prevent. We decided instead to compile every `.erb` under the views root once, at `Boot`, in the main Ractor, into real instance methods on a module `Context` includes, then freeze the registry. This makes a template's syntax error a boot failure naming file and line — ADR 0003's posture extended from routes to views — and makes a render a plain method call whose backtraces point at the `.erb`. It also makes `Monk.boot(App)` in `config.ru` load-bearing rather than merely recommended, since a first request arriving in a worker would otherwise try to compile there. The accepted cost is that the template set is fixed at boot and editing one needs a restart; static assets are deliberately not compiled, so editing CSS or JS still only needs a refresh.

## Considered Options

- A per-Ractor template cache, mirroring `Monk::Persistence::Pg`'s per-Ractor connections (rejected: a connection is an ordinary object a Ractor can own privately, but a compiled template is a method on a module, and a module can't be duplicated per Ractor)
- `eval`ing each template's compiled source in the worker on every request (rejected: genuinely Ractor-safe and only ~18µs against ~2.6µs, but it moves every template syntax error from boot to whichever request first hits that template)
