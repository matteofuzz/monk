# A page resyncs once after its first subscribe is acknowledged, as after a reconnect

ADR 0011 made a refetch of the page the recovery for anything a client may have missed, and ran it after a reconnect or a gap in `seq`. It left out the first connect. The server renders a page, and only later (hundreds of milliseconds on a phone, more on a slow network) does the page's client open its socket and subscribe. A change published in between reaches nobody, and nothing notices: `seq` is per connection and starts with the first envelope after the subscribe, so no gap shows. The page stays wrong until the next patch to that region or a reload; in a chat, a message sent while the other person opens the conversation is missing from it.

We decided that the client resyncs on every connect, the first included, once the server has acknowledged its subscriptions: a change published before the acknowledgement is in the refetched page, and one after it arrives as a patch. The acknowledgement is a sound point with every fanout: `Session#subscribe` replies only after the registry has registered the topics, and the Postgres and Redis fanouts listen on one channel for the whole process. `monk-live:resynced` carries a `reason`, `"first"`, `"reconnect"` or `"gap"`, so an app can treat the load's resync apart. Since every load now reconciles topics after a resync, the client remembers the topics the server denied on a connection and doesn't ask for them again until the next one.

The accepted cost is one more page fetch per load of a page with `data-live-topic` (a page without topics opens no socket and is unchanged), so such a page is rendered twice; Phoenix LiveView renders every page twice by design, for the same reason. The morph after load is usually a no-op, and keeps focus, typed text, `data-live-ignore` and open `<details>` as any resync does; what an app's JavaScript changed in the page at load is morphed back to the server's markup, as after any resync, so that code also runs on `resynced`. Measured on a real app's heaviest Live page before calling 0.29 done (`docs/plan-0-29.md`).

## Considered Options

- The page carries its render time, and at subscribe the server says whether each topic was published to since; resync only then (not now: it needs a last-published time per topic shared by every process, which the fanouts don't keep, and rules for clocks; the optimization to make if the second fetch is measured to matter)
- Subscribe at render time: the server registers a pending subscription under a token, buffers its patches, and the socket claims it (rejected: buffers per page view, an expiry, and claiming across processes, far heavier than a fetch)
- Resync only when the first acknowledgement comes late (rejected: any delay can hide a publish; a threshold is a guess, not a fix)
