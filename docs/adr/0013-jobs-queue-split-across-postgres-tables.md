# Monk::Jobs keeps its queue in several Postgres tables, Solid Queue style, not one GoodJob-style table

Monk needs background jobs (`docs/history/plan-jobs.md`), and there is nothing to adopt. No Ruby job library is Ractor-aware, and the mature ones would break Monk's no-new-dependency rule even if they were. Solid Queue and GoodJob need ActiveRecord, which fails in a worker Ractor for the same reason Sequel did (`docs/design/persistence-ractor-connections.md`). Que and queue_classic run on raw `pg`, but they keep their connection on a module ivar, so enqueueing from a route handler hits the unshareable-module-ivar hazard from `docs/design/ractor.md`. Sidekiq keeps its Redis pool on the `Sidekiq` module, so it has the same problem and needs Redis too. This was reasoned from how each gem is built, not spiked, because every one of them is excluded by the dependency rule anyway. So Monk builds its own queue on Postgres only, the database an app with `--postgres` already runs, and adds nothing to the stack.

We decided the queue is split across several narrow tables, each holding one state of a job's life, the way Solid Queue does it. We rejected one wide table holding every job in every state, the way GoodJob does it. Workers poll only a small table that holds runnable jobs and nothing else, and that table is only ever inserted into and deleted from, never updated. The choice rests on how Postgres handles a busy table, explained below. It was not benchmarked here. `plan-jobs.md` Phase 0 measures claim latency against a large backlog for both designs, and this ADR is revisited if the numbers disagree.

## Why a single table slows down as the queue grows

In a single table, one wide row holds a job's payload, state and lock, so every change of state is an `UPDATE`: insert, then update to claim it, update again to retry or fail it, then update or delete to finish it. Four effects add up as the table grows:

1. **Every update leaves bloat behind.** Postgres writes a new version of the row and leaves the old one dead. An update only avoids new index entries (a "HOT" update) if no indexed column changes. A queue's updates always change the columns its dequeue index filters on (`locked_at`, `run_at`, `finished_at`), so the index fills with dead entries that every poll steps over until vacuum removes them.
2. **The hot index holds rows that can't run.** Future scheduled jobs, jobs waiting to retry, and any finished jobs kept for history share the table. A partial index removes finished rows but keeps scheduled and retrying ones, which `run_at <= now()` then filters out again on every poll.
3. **One slow transaction anywhere stalls cleanup.** A long report or migration holds back the point below which vacuum may remove dead rows, database-wide, and the most-updated table suffers first ([Brandur, "Postgres Job Queues & Failure By MVCC"](https://brandur.org/postgres-queues)).
4. **Lock-then-check dequeue scans candidates.** With advisory locks (GoodJob's default), candidate rows have to be read before they can be locked. GoodJob's own README calls its CTE dequeue "non-performant" beyond about 100,000 jobs and caps it with `queue_select_limit`.

Dequeue cost therefore grows with the whole table and how fast it churns, not with how much work is actually ready. That matches what a GoodJob-style queue does under a long backlog in practice.

## What the split buys, and what it costs

Solid Queue keeps the payload in `jobs`, and a job's state as a row in one of several narrow tables: `ready_executions` (only `job_id, queue_name, priority`), `scheduled_executions`, `claimed_executions` and `failed_executions`, plus a `processes` table for heartbeats. Claiming a job is one transaction that deletes it from ready and inserts it into claimed, using `FOR UPDATE SKIP LOCKED` and leaving `jobs` untouched. A dispatcher moves due scheduled rows into ready in batches. A backlog of a million jobs becomes a million narrow rows in an index that matches the claim query exactly and never sees an `UPDATE`. Scheduled jobs, failures and history never touch a poll.

The cost is about twice the writes per job (roughly 6 on the happy path instead of 3), multi-statement transactions at every change of state, a dispatcher, heartbeat bookkeeping, and invariants that span tables and must never leave a job with no state row or with two. With a short queue the single table is cheaper. The split pays off with a long backlog, many scheduled jobs, or kept history. Monk pays that price because the cost stays bounded as the queue grows, and a framework can't know how long its apps' queues will get.

Monk takes the split but not all of Solid Queue. Version 1 has six tables: `monk_jobs`, `monk_ready_executions`, `monk_scheduled_executions`, `monk_claimed_executions`, `monk_failed_executions` and `monk_processes`. Concurrency limits (blocked executions, semaphores), pauses, recurring jobs and batches are left out. None of them changes the claim path, so each can arrive later as another table. By default a finished job is deleted rather than marked, so the one table that would otherwise grow forever never builds up history.

Two further choices follow from the same reasoning:

- **Workers poll by default and do not rely on `LISTEN`/`NOTIFY`.** A poll against a small, well-indexed ready table is cheap. A `NOTIFY` issued inside a transaction takes a global lock at commit that serializes every committing transaction that notified, which can bring down a database with many writers ([Recall.ai](https://www.recall.ai/blog/postgres-listen-notify-does-not-scale); for a counterpoint, [DBOS](https://www.dbos.dev/blog/postgres-listen-notify-scalability)). Solid Queue polls only for the same reason. `NOTIFY` is an opt-in way to wake idle workers sooner, never how jobs are delivered. `Monk::WebSocket::PgFanout`'s own use of it for Live is unaffected.
- **Claims are released by process, not by row lease or advisory lock.** A claimed row records its process, and a process that stops sending heartbeats has its claims pruned. A per-row lease would bring back an `UPDATE` on every heartbeat. A session-level advisory lock would pin one connection for the whole job and break behind PgBouncer in transaction mode. Pruned claims go back to ready, rather than failing as current Solid Queue does, so delivery is at-least-once and jobs must be idempotent. Solid Queue can fail them because ActiveJob owns retries there. In Monk the queue owns them.

## Considered Options

- **One table, GoodJob style, with advisory locks** (rejected: dequeue cost grows with total size and churn; advisory locks pin a connection per job and break behind a transaction-mode pooler)
- **One table done carefully**: `SKIP LOCKED`, a partial index on runnable rows, delete on success, failures archived to a second table, aggressive autovacuum (rejected, though it was the closest alternative: it fixes the polluted index and the candidate scan, but claiming a job is still an `UPDATE` of an indexed column on a wide row, which is exactly the churn the split removes)
- **Full Solid Queue schema, including concurrency controls, pauses, recurring tasks and batches** (not taken for v1: none of these changes the claim path, so each can be added later as its own table without redesign)
- **Redis lists (`LMOVE` reliable queue, a sorted set for scheduled jobs)** (rejected for v1: a second piece of infrastructure for apps that only run Postgres, no enqueue inside the app's own transaction, and retry and scheduling logic that has to be written in Lua to be atomic; still open as a second adapter if Postgres throughput ever becomes the limit)
- **An in-memory queue only** (rejected as the production design: jobs are lost on every restart or deploy, and work can't be spread across processes. Kept as a second adapter behind the same interface for tests and development, the same way `RedisFanout` and `PgFanout` sit behind `Registry`'s interface)
- **`LISTEN`/`NOTIFY` as the queue itself** (rejected: notifications aren't stored, are lost when nobody is listening, and are capped at 8000 bytes, as `PgFanout` measured)
- **Adopt an existing gem** (rejected: each needs a new dependency, and each keeps module-level state that a worker Ractor can't read, as described at the top)
