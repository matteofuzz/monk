# Monk::Jobs keeps its queue in a narrow state table plus a payload table, not in one wide table or Solid Queue's split

Monk needs background jobs (`docs/history/plan-jobs.md`), and there is nothing to adopt. No Ruby job library is Ractor-aware, and the mature ones would break Monk's no-new-dependency rule even if they were. Solid Queue and GoodJob need ActiveRecord, which fails in a worker Ractor for the same reason Sequel did (`docs/design/persistence-ractor-connections.md`). Que and queue_classic run on raw `pg`, but they keep their connection on a module ivar, so enqueueing from a route handler hits the unshareable-module-ivar hazard from `docs/design/ractor.md`. Sidekiq keeps its Redis pool on the `Sidekiq` module, so it has the same problem and needs Redis too. This was reasoned from how each gem is built, not spiked, because every one of them is excluded by the dependency rule anyway. So Monk builds its own queue on Postgres only, the database an app with `--postgres` already runs.

We decided the queue lives in two tables. `monk_jobs` is narrow: `queue`, `priority`, `state` (`available`, `scheduled`, `running`, `failed`), `run_at`, `attempts`, `max_attempts`, `locked_by`, `locked_at`, about 70 bytes a row. `monk_job_payloads` holds `job_class`, `args` and `last_error`, and is written once at enqueue and deleted with its job. Each lookup gets a partial index covering only the rows it wants: `(queue, priority, run_at, id) WHERE state = 'available'` for claiming, `(run_at) WHERE state = 'scheduled'` for promoting due jobs, `(locked_by) WHERE state = 'running'` for crash recovery. A third table, `monk_processes`, holds one heartbeat row per job process. Claiming a job is one `UPDATE` of a narrow row, using `FOR UPDATE SKIP LOCKED`, joined to its payload. Finishing is one `DELETE`, and the payload goes with it by cascade. A small stager, run on the job process's supervisor tick, flips due `scheduled` rows to `available` in batches, so scheduled jobs and retries never sit in the index workers read. Failed jobs stay in `monk_jobs` as `state = 'failed'`, outside every hot index, and retrying one is a single `UPDATE`.

This replaces this ADR's first version, written the same day, which chose Solid Queue's six-table split (jobs, ready, scheduled, claimed and failed executions, processes). That version rested on reasoning. `plan-jobs.md` Phase 0 then measured it against the alternatives, with 8 worker Ractors on Postgres 16, 150 s of steady load at about 2,000 jobs/s and ~1 KB of args. Those measurements changed the decision.

## What the measurements showed

- **Backlog length alone costs nothing in any design.** Taking the head of a B-tree cost about 1 ms at 10k, 100k and 1M ready jobs alike. The first version's claim that a single table slows down as the queue grows, and that scheduled rows pollute its index, did not hold for a carefully built single table (`SKIP LOCKED`, a partial index, ordering by `run_at`, delete on finish). The exception, found later, is scheduled rows combined with priorities (below).
- **With vacuum keeping up, every design is the same.** All four candidates claimed in about 1 ms and processed about 1,950–1,990 jobs/s. They differed only in WAL per job: 0.90 KB for a narrow table without a state column, 1.08 KB for this design, 1.12 KB for the six tables, and 1.39 KB for one wide table, whose claim rewrites the whole payload-carrying row.
- **With vacuum held back, the designs separate.** A transaction held open in the same database for the whole run stops vacuum from removing dead row versions, so deleted and updated rows pile up at the head of the index. Median claim time after 150 s: 11.2 ms for the six tables (927 jobs/s), 12.8 ms for this design (917), 14.5 ms for a narrow table without a state column (852), 26.6 ms for one wide table (547). A wide row leaves more dead bytes behind for every job than a narrow one.
- **No design is immune, and a separate database isolates all of them.** Postgres only holds back cleanup of an ordinary table for transactions in that table's database. With the same long transaction held in another database on the same server, every design tested that way (the six tables, the wide single table, and this one) stayed flat at about 1 ms. This is why Rails 8 gives Solid Queue its own database by default. It doesn't help against a long transaction inside the queue's own database, or against holders that span the whole server (replication slots, `hot_standby_feedback` from a replica).
- **Scheduled rows need to stay out of the claim index.** With 100k future jobs at priority 0 and ready jobs at priority 10, a narrow table without a state column claimed in 5.5 ms, reading 606 buffers, because every claim stepped over the future rows sorted ahead of it. With the `state` column and an index on `available` only, the same data claimed in 0.96 ms, reading 4 buffers. That's what the stager costs and buys: up to one tick (about 1 s) of extra delay for a scheduled job, and one extra narrow `UPDATE` per scheduled job. Jobs enqueued to run immediately skip it.

So this design keeps the six tables' resilience within about 1% on throughput and 15% on latency, and all of the benefit of a separate database. It does that with three tables, no dispatcher process, scheduling and retries as plain `UPDATE`s, and no invariants spread across state tables that must never leave a job in zero or two of them. For a minimalist framework, that margin isn't worth three more tables and the transactions that move a job between them.

## Related decisions from the same analysis

- **Workers poll and do not rely on `LISTEN`/`NOTIFY`.** A poll against a small partial index is cheap. A `NOTIFY` issued inside a transaction takes a global lock at commit that serializes every committing transaction that notified, which can bring down a database with many writers ([Recall.ai](https://www.recall.ai/blog/postgres-listen-notify-does-not-scale); for a counterpoint, [DBOS](https://www.dbos.dev/blog/postgres-listen-notify-scalability)). `NOTIFY` stays an opt-in way to wake idle workers sooner, never how jobs are delivered.
- **Claims are released per process, not by a lease on each row or by advisory locks.** A running row records its process in `locked_by`. A process whose heartbeat has expired has its running jobs set back to `available`, so delivery is at-least-once and jobs must be idempotent. A lease on each row would add an `UPDATE` per heartbeat. A session-level advisory lock would pin one connection for the whole job and break behind PgBouncer in transaction mode.
- **The queue uses the app's database by default, and a separate database is documented as the step to take under load.** In the same database, `enqueue` can run inside the app's own transaction, so a job and the data it acts on commit or roll back together, which Redis or an in-memory queue can't offer. The price is exposure to the app's long transactions. A separate database (`Monk::Jobs.configure(db_name: :queue)`) removes that exposure, but enqueue then happens after the app's commit, and a crash in between can lose the job. The guide names long transactions on the queue's database as the main operational risk, and recommends `idle_in_transaction_session_timeout` and per-table autovacuum settings.

## Considered Options

- **Solid Queue's split** (`jobs`, `ready`/`scheduled`/`claimed`/`failed` executions, `processes`) (runner-up: measured best by a small margin when vacuum is held back in the same database, but it needs a dispatcher, moves each job between tables in multi-statement transactions, and has rules that span tables, for a margin a separate database removes anyway)
- **One wide table built carefully** (`SKIP LOCKED`, a partial index, order by `run_at`, delete on finish) (rejected: as fast while vacuum keeps up, but each claim rewrites the wide row, which meant 29% more WAL than this design and a claim time twice as bad once vacuum was held back)
- **One wide table, GoodJob style**, with advisory locks and finished jobs kept in the table (rejected: the retained-rows variant measured like the careful table at best; the advisory-lock CTE was not benchmarked, but GoodJob's own README calls it "non-performant" beyond about 100,000 jobs, and advisory locks pin a connection per job)
- **A narrow table plus payloads without a `state` column**, with future jobs as `run_at` in the claim index and no stager (rejected: the least WAL of all, but scheduled rows at a more urgent priority sit ahead of every claim, which measured 5.7 times slower with 100k of them)
- **Redis lists** (`LMOVE` reliable queue, a sorted set for scheduled jobs) (rejected for v1: a second piece of infrastructure, no enqueue inside the app's own transaction, and retry and scheduling logic that must be written in Lua to be atomic; still open as a second adapter if Postgres throughput ever becomes the limit)
- **An in-memory queue only** (rejected as the production design: jobs are lost on every restart or deploy, and work can't spread across processes. Kept as a second adapter behind the same interface for tests and development, the way `RedisFanout` and `PgFanout` sit behind `Registry`'s interface)
- **`LISTEN`/`NOTIFY` as the queue itself** (rejected: notifications aren't stored, are lost when nobody is listening, and are capped at 8000 bytes, as `PgFanout` measured)
- **Adopt an existing gem** (rejected: each needs a new dependency, and each keeps module-level state that a worker Ractor can't read, as described at the top)
