# After a reconnect or a missed patch, the client resyncs by refetching the page and morphing it in

A patch protocol is only correct if a client that missed patches can converge again. Each envelope carries a per-connection `seq`, and when the client sees a gap or reconnects it must recover current server state. We decided that recovery is a full refetch of the current page URL, morphed over the live DOM with the same focus-protection and `data-live-ignore` rules as any patch, after which patches resume, so the page's own view stays the only definition of what a region looks like and no second, separately maintained snapshot definition can drift from it. That makes patches purely an optimization over "the page can always be re-fetched", and it makes the protocol's `resync` message something the server may answer either way. The accepted cost is that a resync is heavier and coarser than re-rendering only the affected regions, and that a much larger morph than a single fragment is untested (the client spike only exercised fragment-sized morphs). The runtime must also stop rather than morph if the refetch returns something that is not the app page, such as a 401 or a redirect to a login screen. Explicit per-topic snapshots (`Monk::Live.snapshot("contacts:*") { ... }` returning per-target partials) are recorded in `PLAN-LIVE.md` as a possible later evolution, to be adopted only when refetch cost or latency is measured to be a problem in monk_talk.

## Considered Options

- Explicit per-topic snapshot definitions (rejected for v0: a second definition of a region's markup that can drift from the page's initial render, plus a naming convention tying topics to regions, for a saving nobody has measured a need for)
- Reuse the page's view for just the regions carrying `data-live-topic` (rejected for v0: needs a convention for which part of a view belongs to which topic, and a page view may depend on request state a detached render lacks)
- No resync, reconnect and hope (rejected: the failure is a silently stale page, which is the two-source-of-truth bug this design exists to avoid)
