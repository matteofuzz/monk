# A fragment is rendered once, in the publishing Ractor, and broadcast as a frozen string

A change that reaches many connections could be rendered by each connection's own Ractor, by a dedicated renderer Ractor, or once by whoever published it. We decided the publisher renders, once, and broadcasts the finished envelope, so connection Ractors only forward bytes. The Phase 0 spikes justify each part of that. Rendering works as-is from a non-main Ractor with a detached `Monk::Context.new({})`, including nested partials, HTML escaping and `asset_path`, at about 3µs per render, so no extra machinery is needed and cost is not a reason to spread rendering out. Delivery is the real cost, roughly linear-to-worse in subscriber count and nearly independent of fragment size, which is what "render once, send many" is for. Broadcasting a shareable (frozen) string passes it by reference instead of copying it per port, which about halved the broadcast call at 500–1,000 connections and cut it about 5x at 1,000 connections and 50KB, so the publisher freezes the payload before it broadcasts. Four consequences are rules, not options: the publishing process must have run `Monk.freeze!` (without it a Ractor render raises `Ractor::IsolationError` on `Monk::Views`' registry, and `Monk::WebSocket::Server` only freezes when `authenticate: true`), so Monk::Live fails fast in the ADR 0003 posture, at the first render, with the fix in the error message (`Monk::Live.configure` cannot itself call `Monk.freeze!`, since it may run before an app has set its views root, so freezing stays with `Monk.boot`/`Monk.freeze!`); the renderer forces `layout: false`, because the default layout wraps a fragment in `<html><body>`; live partials are request-independent, since a detached context has no `params`, session or per-request helpers and everything a fragment needs arrives as locals (a per-viewer fragment passes the viewer as a local); and a template reads its data as `locals[:contact]`, not a bare variable, as it does everywhere else in Monk. A fragment whose content differs per recipient is a deliberate exception that renders once per recipient and gives up the shared-render saving. The open question of whether persistence data crosses the Ractor boundary as a local is settled by Phase 1: `Monk::Persistence::Pg::Model` returns plain Hash rows, not model instances, and an unfrozen Hash row (with a `Time` and a `nil`) is copied into a Ractor and renders fine.

## Considered Options

- Each connection Ractor renders its own copy (rejected: multiplies identical work by the subscriber count and makes every connection Ractor need views frozen and app data reachable)
- A dedicated renderer Ractor (rejected for v0: the spike showed a plain publisher-side render is enough, so it adds a hop and a queue for no measured gain; still open as an option if rendering ever needs isolating)
- Render lazily on first send per connection and cache (rejected: a cache is shared mutable state, the class of design ADR 0004 already ruled out for templates)
