# Monk::Live is a separate, opt-in layer above Monk::WebSocket, not a WebSocket feature

`Monk::WebSocket` already carries opaque text frames between a browser and a per-connection Ractor, and `docs/reactive-partials.md` left open whether reactive fragment patching should be a new message type inside it or something built on top. We decided on the latter: `Monk::Live` is a module beside them in `lib/monk/`, opt-in like `Monk::WebSocket` and `Monk::Auth` (`require "monk/live"` explicitly; `require "monk"` alone never loads it), that uses `Server`, `Connection` and `Registry` as they are and defines only what goes inside the frames. It depends on `Monk::WebSocket` and `Monk::Views`, and neither depends on it, so `Monk::WebSocket`'s wire code and its own tests do not change. This also removes the doc's reason to wait for the multi-process fan-out question: a `Registry`-shaped publisher interface is what `RedisFanout` already wraps transparently, so cross-process delivery is inherited rather than redesigned. It starts in this gem (`lib/monk/live.rb` and `lib/monk/live/`) and the one-way dependency keeps extraction into its own gem cheap. The accepted cost is that anything Monk::Live needs from the socket layer (a per-connection `seq`, a place to run the subscribe handler) has to be reachable through the existing public `Connection` and `Registry` surface or added there as a small, separately justified change.

## Considered Options

- Add patch/subscribe as message types inside `Monk::WebSocket::Server`/`Connection` (rejected: turns a deliberately dependency-free transport into one that knows about views, topics and authorization, and forces every WebSocket app to carry it)
- A top-level `MonkLive` outside the `Monk` namespace (rejected: an earlier draft argued a top-level name makes the opt-in explicit, but `Monk::WebSocket` and `Monk::Auth` are already opt-in under `Monk` and nothing autoloads, so it bought nothing and broke the `lib/monk/` convention)
- A separate gem from day one (rejected: premature while the API is still moving; the one-way dependency keeps that option open)
