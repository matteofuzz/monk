# Presence is kept as per-process rows in Postgres, read by any process, and each change of status is settled once in a status table

An app wants to show whether a person is online, on phones as well as desktops (roadmap item 3, `docs/plan-live-networks-presence.md`). The page that shows the status is rendered by `bin/server`, which holds no sockets. The sockets are in one or more `bin/websocket_server` processes, possibly on several hosts, any of which can stop or crash without cleaning up. A connect must not cost a query, since a WebSocket deploy reconnects every page within seconds (25K in the connect benchmark). A phone that switches network is offline for a few seconds, and a deploy drops every socket at once, and neither should read as "went offline" to the people watching. What a phone does to a socket was measured on real devices for this decision (the plan's A0): a locked iPhone resets the page's socket after about 16 s (3 s after switching apps), Android keeps it for about 5 minutes in Chrome, and both come back within a second of being looked at again.

Already decided in the plan: presence lives in Postgres, even for apps on the Redis transport (open question 4); only `Monk::Auth` subjects are tracked, one subject counted once across tabs and devices (B0, item 8); Away is inferred from the Live client's heartbeat (open question 6), and since 2026-11-13 also from a `{"op":"hidden"}` message the client sends as its page is hidden; it ships as `monk add presence` (open question 5).

We decided that each WebSocket process counts its own sockets in memory, per subject, and writes what changed once a second as rows of its own in an `UNLOGGED` table, `monk_presence (process_id, subject, status, gone_at)`. `status` is `online` (a visible page open) or `away` (only hidden pages). When a subject's last socket in that process closes, the row isn't deleted: it gets `gone_at` and keeps the status it had. Each process keeps a heartbeat row in `monk_presence_processes (id, hostname, pid, heartbeat_at)`, as `Monk::Jobs` does. A row counts while its process is alive (heartbeat within `PROCESS_TIMEOUT`) and, once gone, for `grace` more. A subject's status is the best of its counting rows, `online` over `away`, and `offline` without any. Readers compute that with one query, from any process. Every WS process's tick also settles transitions into a logged table, `monk_presence_status (subject PRIMARY KEY, status, changed_at, last_seen_at)`, with an upsert that only writes, and only returns, a status that differs from the stored one. Exactly one process gets each transition back. In the same transaction it sends one `NOTIFY monk_presence` listing the subjects that changed. The WS process never runs app code: the reaction is in `bin/server`, where one Ractor, elected among the web processes, listens, reads those subjects' current status and calls the app's `on_change` hook with the batch. Every time is the database's `now()`, so hosts' clocks don't matter.

## How the pieces fit

- **Counting, no query per connect.** `Server.serve` tells a per-process presence Ractor when an authenticated socket opens (after the 101) and closes (in its ensure), with a send, not an ask, so a connect never waits on it. The Ractor holds subject → open sockets and visible sockets, and which subjects changed since the last flush. A flusher thread in the main Ractor takes that diff once a second and writes it in one statement (arrays through `unnest`: upsert the subjects with sockets, set `gone_at = now()` on those down to zero). Nothing is remembered for a subject once its zero is written. A reconnect to the same process in the grace upserts the row back to `gone_at = NULL`.
- **Away, from the Live heartbeat.** A Live socket is visible while the server has had a `{"op":"ping"}` from it within `2 × HEARTBEAT` (50 s). `Live::Session` tells the presence Ractor when a socket crosses that line, either way. A Live socket starts out hidden. The client pings at once on open when its page is visible, so a visible page is online within a frame, and a hidden page's reconnect doesn't read as Online. A socket that never sends Live pings (an `app/sockets` client) counts as visible: it has no Away. The server's `HEARTBEAT` mirrors `protocol.js`'s, with a test that fails if they differ. So the client's ping schedule is part of what Away means: changing when the client pings changes Away, and this ADR is where that rule is written. The client also sends `{"op":"hidden"}`, with no reply, on `visibilitychange` to hidden, and `Live::Session` marks the socket hidden at once. Away then shows on the next tick, not 50–75 s later. The 50 s of silence stays as the fallback for a page frozen before the message got out (iOS can suspend a page first). It is checked on the connection's own heartbeat, after each server ping (`Connection#on_heartbeat`), so a silent page turns Away 50–75 s after its last ping. A first version gave each Live connection a thread of its own for it, waking every 10 s: at 15K open sockets those threads alone took the WebSocket process from 40% to 83% CPU and failed a third of the connects (`bin/benchmark_ws_connect --presence`).
- **Grace before offline, where the row is.** A closed socket's row keeps counting, with its last status, for `grace` (20 s by default, `Monk::Presence.configure(grace:)`). A subject reconnecting anywhere in that time never reads as offline. Online and Away change without grace: hiding and showing a page are meant to show at once.
- **A process that stops.** On `TERM` it sets `gone_at = now()` on all its rows and stops heartbeating. The rows count for the grace, while its pages reconnect to the new process, so a deploy changes nobody's status. Deleting its rows instead would turn everyone offline for the second it takes them to reconnect.
- **A process that crashes.** Its rows count until its heartbeat is older than `PROCESS_TIMEOUT` (30 s, heartbeat every 5 s on the flush tick). Its pages reconnect to another process within a second, so only subjects with nowhere else to go turn offline, about 30 s after the crash.
- **Settling and pruning, by any process.** Each tick, a WS process takes the subjects it just flushed and those whose rows have expired (gone past the grace, or of a dead process), settles them into `monk_presence_status`, and deletes the expired rows and dead processes, in one transaction. The upsert's `WHERE status IS DISTINCT FROM excluded.status` makes a second process settling the same subject see no change once the first has committed, so each transition is returned once. The settling transactions also take a transaction-scoped advisory lock (`pg_advisory_xact_lock`), so processes settle one at a time. Without it, one process could settle from a snapshot taken before another's flush committed, and record a stale status. Going offline, `last_seen_at` is taken from the expired rows: the latest `gone_at`, or a dead process's last heartbeat. A full reconcile of every non-offline subject runs every minute too, for transitions no expiry announces: the `UNLOGGED` rows emptied by a Postgres crash, or a process that came back with a new id.
- **Readers.** `Monk::Presence.status(subjects)` returns `{subject => {status:, last_seen_at:}}` (`:online`, `:away` or `:offline`; `last_seen_at` for the offline ones), and `online?(subject)`. One query for the people on screen: the counting rows for those subjects, joined to their processes, plus `monk_presence_status` for `last_seen_at`. Readers derive the status from the rows, not from `monk_presence_status`. If every WS process is down, nobody settles, and a stored `online` would never turn `offline`, while rows of dead processes stop counting by themselves. An offline subject whose rows expired but haven't been settled yet (up to a tick) gets its `last_seen_at` from those rows, as settling would.
- **The signal: one `NOTIFY` per settle, listing subjects.** The settling transaction sends `NOTIFY monk_presence` with a JSON array of the subjects whose status it changed. Postgres delivers a notify only when its transaction commits, so the signal never arrives before the status it announces. A payload is capped under 8000 bytes, so a large batch is split into several notifies (about 600 subjects of the form `user:12345` each). They belong to the same transaction and are delivered together, in order. The signal carries no status: it says "these subjects changed", and the reaction reads their current status. So a signal that arrives late, twice or out of order still leaves the page right. Nothing is sent when the app has no `on_change`: `config/presence.rb` sets it, and the WS processes load that file too, so they know without a setting of their own.
- **The reaction: a Ractor in `bin/server`.** The web process holds the app's code and views, and already renders and publishes Live patches. So when `bin/server` boots with presence configured and an `on_change`, it starts one background Ractor. That Ractor opens its own Postgres connection and takes a session advisory lock with `pg_try_advisory_lock`. The one that gets the lock `LISTEN`s on `monk_presence`. The others retry every few seconds, and take over when the holder's connection ends: Postgres releases its lock then. The reactor is a single thread that waits in steps of half a second: with a second thread waiting in Postgres, the Ractor failed to handle a stop message about half the time in tests. For each signal, the reactor calls `Monk::Presence.status(subjects)` once, then `on_change` with the result. `bin/jobs`, `bin/console` and the WS process never react.
- **`on_change`.** `Monk::Presence.on_change(&AppPresence::CHANGED)` in `config/presence.rb`, with a block that receives a batch, `{subject => {status:, last_seen_at:}}`. The block is built in a module, so it's Ractor-shareable, like `Live.authorize` rules. The app calls `Monk::Live.patch` from it, per subject or coalesced: a batch lets an app send one patch for many changes. An error in the hook is logged and doesn't stop the reactor.
- **Across hosts and pods.** Nothing is shared but Postgres: process rows, the settle lock and the reactor's lock are all Postgres's, so WS processes and web processes on several hosts behave as several on one. The reactor's connection is the one place a host matters:
  - A reactor whose host vanishes without closing its connection (a lost node, a cut network) would keep the lock until Postgres's TCP keepalive gave up, about 2 hours with Linux's defaults, and no process would react. So its session sets `tcp_keepalives_idle = 10`, `tcp_keepalives_interval = 5` and `tcp_keepalives_count = 3`, which any user may set for their own session, and Postgres drops it in about 25 s. Its client-side keepalives are the same, for a Postgres host that vanishes.
  - Its lock and its `LISTEN` belong to its session, so it needs a direct connection, not PgBouncer in transaction mode, like the WebSocket transport's `LISTEN`. Settling is plain statements and works through it.
  - Every web process holds one connection for its reactor, waiting or listening, and the one listening opens one more for its status reads: N web processes, N + 1 connections.
- **Delivery is at most once.** A `NOTIFY` sent while no reactor listens is lost: during a web deploy or failover (up to the retry interval), or when every `bin/server` is down. A page missing a change is current again on its next resync (reconnect, gap, visibility), and on its next render. That's acceptable for a live dot, and it's the documented contract.
- **Patch volume.** A reactor can patch faster than the `:notify` pool (one connection, at most 1000 calls waiting) can send: in the spike, 20K patches in a burst under HTTP load dropped 416 with `PoolFullError`. This happens for any burst of `Live.patch`, wherever it comes from. Batched signals let an app coalesce, and the guide says to: patch per page, not per person, when many change at once.
- **Failures.** In the WS process, the flusher, heartbeat and settling run on one thread of the main Ractor, through that Ractor's own connection. No app code runs in the WS process, so nothing else uses that connection. An error is logged, never ends the process, and the next tick rewrites all the process's rows from memory, marking gone any open row it no longer has. While it can't write, its rows stop counting after `PROCESS_TIMEOUT`, so its subjects can read as offline until it's back. In `bin/server`, a reactor that loses its connection reconnects and competes for the lock again.

## The reactor, measured

A spike on 2026-11-13 ran a Ractor started in `config.ru`, after `Monk.boot`, in a real `bin/server`: Kino 0.7.2, 8 worker Ractors, on a laptop. The Ractor `LISTEN`ed and, for each notify, rendered a partial and called `Monk::Live.patch`.
- It ran alongside the workers with no Kino hook.
- From notify sent to patch published: p50 0.34 ms, p99 1.23 ms, max 6.5 ms over 5000 notifies.
- Throughput with 32 concurrent requests: 20.1K req/s with the reactor idle, 16.0K req/s during a 20K-notify burst. p99 went from 4 ms to 7 ms, with no failed requests.
- On `TERM`, Kino drained and exited in about 0.5 s with the Ractor blocked in `LISTEN`.

## A connect wave, measured

`bin/benchmark_ws_connect --variant live --presence` on 2026-11-13, in the `bench-monk` Linux container on a Mac (server on 4 cores, Ruby 4.0.7), connecting 15K and 25K signed-in Live sockets at 100/s and holding them, with and without presence, `--ping-interval 600` both ways (the benchmark's client doesn't answer pings):

- **Statements:** about 2 store calls a second during the wave (a flush, a settle, a heartbeat every 5 s), whatever the connect rate: 312 for 15K connects, 443 for 25K.
- **15K held:** all 15,000 ready either way; p99 725 ms with presence, 1,700 ms without; server CPU 43% and 46%.
- **25K held:** both at Ruby 4.0's GC ceiling on this machine (about 100 s of GC over the wave), 21,807 ready with presence and 20,604 without: no difference presence makes.
- **The first version** gave each Live connection a thread for the silence check, waking every 10 s. At 15K it took CPU from 40% to 83% and only 10,266 of 15,000 connects succeeded. Moving the check onto the connection's existing heartbeat removed that cost.

## What a status means, measured

- **A locked iPhone is Offline** about 36 s after locking (16 s for iOS to reset the socket, then the grace), and Online again within a second of unlock. Without `{"op":"hidden"}` it read Online, not Away, until then: iOS resets the socket before 50 s of missing pings make it Away. With it, Away within a second (below). Telling "phone in a pocket" from "closed the app" isn't possible through a WebSocket on iOS. That is what Reachable is for, 0.25's push subscriptions, kept by the app. A longer grace for sockets closed while hidden was considered and left out: it would show Online for a phone that can't receive anything.
- **A locked Android phone is Away** after about 50 s and Offline after about 5 minutes in Chrome, when Android resets the socket.
- **A hidden desktop tab is Away** after about 50 s, and Online at once when shown (the client's probe ping). With `{"op":"hidden"}` (added after these measurements), Away within a tick of hiding: seen on a Mac on 2026-11-13, where a fully covered browser window counts as hidden too. Measured again with it on 2026-11-13, an iPhone (Safari) against the scaffolded app: Safari sends the message as the screen locks, so a locked iPhone is **Away within a second**, **Offline 24 s after locking** (iOS dropped the socket within a few seconds, then the grace), and Online 0.4 s after unlock (probe, reconnect, resync). On Android (Chrome), the same day: a page in a background tab is **Away at once**, and was still Away after 8 minutes, Offline only once Chrome was closed. Chrome's network layer keeps answering the server's WebSocket pings for a hidden page, so its socket lives as long as Chrome keeps it: Away can last for hours on Android, where on iOS it turns Offline in about 24 s. The ~5 minutes above is when Android stopped Chrome on a locked phone, and depends on the device's power settings.
- **Visible isn't "at the keyboard"**: an unattended desktop tab reads as Online. Idle detection is out of scope.
- **Offline shows after** the close plus the grace (20 s), or the process timeout for a crash (30 s), plus up to a tick. A peer that vanished silently is first closed by the server's idle timeout, `2 × ping_interval` (50 s in the scaffold).

## Tables

- `monk_presence` and `monk_presence_processes` are `UNLOGGED`: rows are rewritten all the time, skipping the WAL is the point, and after a Postgres crash they come back empty and each WS process rewrites its own. To confirm by measurement in B1 (a 25K connect wave, logged against unlogged). Unlogged tables don't reach read replicas, so presence is read from the primary. Monk doesn't route reads to replicas today, and the guide says so.
- `monk_presence_status` is logged. `last_seen_at` is shown to users and must survive a crash, and it is written once per transition, not per connect. It keeps one row per subject ever seen, like the sessions an app already has.
- One numbered migration in the `presence` template, `00000000000005_create_presence_tables`, written by `monk add presence`.

## Considered Options

Where the shared state lives:

- **Each process's memory, shared through the fanout** (rejected: `bin/server` has no sockets and nothing to ask, and a process started late never hears who joined before it)
- **Redis, a hash per process with a TTL** (rejected: only apps on the Redis transport have it, and presence needs `Monk::Auth`, so Postgres anyway, plan open question 4)
- **Postgres** (chosen)

Where the grace and the transitions are decided:

- **Delete a process's row when its count reaches zero, and let readers see offline at once** (rejected: every network switch and every deploy reads as going offline)
- **A delayed job per going-offline subject, checking again after the grace** (rejected: a job per close in a reconnect wave, and `Monk::Jobs` would become a requirement of presence)
- **The process that saw the close decides after the grace, from memory** (rejected: the process that saw it may be the one stopping, and it can't know whether another process has the subject)
- **Rows kept with `gone_at` for the grace, readers deriving status, transitions settled by an upsert any process runs** (chosen: readers need no writes and are right even with every WS process down, deploys don't flap, and no single process has to survive for a transition to happen)
- **The status table as the only truth for readers** (rejected: with every WS process down, nobody settles, and statuses stay `online` forever)

Away:

- **Inferred from Live's own heartbeat** (chosen, plan open question 6), **plus `{"op":"hidden"}` when the page is hidden** (added 2026-11-13, after trying the scaffold on a Mac and an iPhone: a dot taking 50–75 s to turn Away looked broken. One message, no reply; showing again needs none, the probe ping does it)
- **Only the heartbeat** (first chosen, then replaced: no new message type, but Away 50–75 s late)
- **A `{"op":"visibility"}` message both ways** (rejected: the probe ping already says visible)
- **Closing hidden pages' sockets and deriving Away from how recently they were seen** (rejected: no live updates in background tabs, and a refetch on every return)
- **Left to apps** (rejected: only possible through a second channel, an HTTP post or another socket, which races the Live one)

Hearing about changes:

- **`on_change` in the WS process that settled the transition** (rejected: the WS process would have to load the whole app, with its views and every module's settings, and a slow hook would hold up the tick that heartbeats, until the process looks dead to the others)
- **Settling enqueues a job, and `bin/jobs` reacts** (rejected: durable and claimed once, but `Monk::Jobs` would become a requirement of presence, and a table row and a claim are too much for a notification)
- **The reactor in `bin/server` polling `monk_presence_status.changed_at` each second** (rejected: a query a second for nothing and up to a second more latency, with the same need for a single poller)
- **A durable change log the reactor drains** (left out: it would make delivery at least once, but a missed dot is fixed by the next resync. It can be added later behind the same `on_change`)
- **One `NOTIFY` per transition, carrying its status** (rejected: up to thousands of wake-ups in a burst, a status that can arrive out of order, and no way for the app to coalesce)
- **One `NOTIFY` per settle listing the subjects, a reactor Ractor in `bin/server` elected by advisory lock, reading the current status** (chosen)
- **Apps polling `status`** (rejected: loses what makes it live)
- **A Live topic Monk publishes presence to** (left out: which pages show whose status, and how, is the app's; it can publish from `on_change` in one line)

Also left out: presence for anonymous sockets (a future route is a `Monk::Auth` session for any subject, such as `"guest:…"`, plan B0 item 8), a Redis store behind the same reader API (possible later without breaking anything), presence history, and idle detection.
