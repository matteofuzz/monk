# The scaffold is one generator per module, run by `monk add` on any app, and generators only create files and append lines

`monk new` took one flag per Monk module (`--postgres`, `--auth`, `--mail`, `--jobs`, `--redis`, `--live`), and each new flag added files, text anchors to edit after copying, whole-file overrides, flags implied by other flags, rules for pairs of flags, and branches in a generated SETUP.md. `lib/monk/scaffold.rb` reached about 1060 lines, 600 of them SETUP.md text. The flags were described in three places (`monk --help`, `docs/guides/scaffolding.md`, SETUP.md), and `--help` had already drifted from ADR 0015's layout. A flag also only worked when the app was created: an app made without `--jobs` got jobs only by hand. Storage and recurring jobs were about to add more of the same. We decided how the scaffold is built instead (`docs/history/plan-scaffold.md`).

**One generator per module, run on any app.** `monk new NAME` writes a bare app. `monk add MODULE` adds a module to an app, new or existing, and `monk new NAME --with a,b` is shorthand for both. A module counts as installed when its config file exists, and adding it again does nothing. A module's dependencies are added first, automatically (`auth` adds `postgres` and `mail`). The old flags are gone: each one is a usage error that shows the new form of the same command. Monk is pre-1.0, and one app has been built from the scaffold.

**Generators only create files and append lines.** A generator copies new files, appends lines to the end of `Gemfile`, `.gitignore`, `.dockerignore` and the `.env` files (skipping lines and keys that are already there, so an app's own values win), adds timestamped migrations, and appends its own section to `SETUP.md` and `AGENTS.md`. It never edits a file in the middle, and never replaces one. That's what makes the result independent of which other modules exist and of the order they were added in. A file the generator would create that already exists with different content is a conflict, handled by its role: on a wiring file (config, `bin/`, a migration, a file a config requires) the whole command stops before writing anything, and on an example, test, view or demo the file is left alone and reported.

**Rules between modules move into the framework or into static files.** Every rule that depended on two flags at once is gone from the scaffold:

- `config/load.rb` is static. It lists Monk's modules in a fixed order and requires each config that exists, so no generator edits it.
- `Monk::Mail.deliver_later` is loaded by whichever of `monk/mail` and `monk/jobs` is required second. The login-link job ADR 0014 had the scaffold write becomes `Monk::Auth::SendLoginLink`, defined the same way when auth and jobs are both loaded. `JOBS_QUEUES` defaults to `mailers,default` whether or not the app sends mail.
- `auth` and `mail` write separate mailer files.
- The base layout calls `monk_head`, which renders the `<head>` tags of the loaded modules (Live's), so the layout is never edited. Monk serves Live's browser client from the gem.
- Dotenv is always in the base Gemfile, and the base Dockerfile doesn't depend on the modules.

**Each module brings wiring, commented examples and a test.** Wiring (config, gem, env vars, migration, `bin/` process) runs as soon as the module is added. The code an app writes to use the module (routes, a subscribe rule, a mailer call, a query) comes as commented blocks, tagged `# monk:example <name>` ... `# monk:end`, in the file where that code would go. Some of these decide the app's security or data model (a login route's rate limit, an access check on downloads, an uploads table), and a working default would be wrong for most apps. Monk's own suite uncomments every block, boots the app and calls it, so the examples follow API changes. Each module also writes a test into the app's `test/` that proves its wiring (a job enqueued and drained, a login token redeemed, mail delivered to `log://`), so the proof stays in the app and returns an exit code. The base app now includes the test setup that every module's test uses. Only `live` also gets a demo, because the failure that matters there (ports, origins, the WebSocket URL) shows only in a browser: `/demo/live`, defined in development only, in its own files, skipped with `--no-demo`.

**Routes added by a module go in `app/routes/<module>.rb`.** `app/app.rb` ends with one line that loads `app/routes/*.rb`, and each of those files reopens `class App`. This amends ADR 0015, which kept every route in `app/app.rb`: the alternative is a generator editing the user's own `app/app.rb`, which an app that already exists can't allow.

**Redis is a module, and WebSocket is a module that chooses a transport once.** An app may want Redis for its own reasons (a cache, rate limits) without sockets. `bin/websocket_server` is no longer part of the bare app, because sockets need something to carry messages between it and `bin/server`: `monk add websocket --transport=postgres|redis` writes `config/websocket.rb`, which builds one registry over the chosen transport, and adds that module if it's missing. When exactly one of the two is installed, the transport can be left out. Live reuses the same registry and has no transport of its own. Changing the transport later is documented, not a command.

**Generated apps get an `AGENTS.md`, and `monk` answers in text or JSON.** `AGENTS.md`, imported by a `CLAUDE.md`, describes the layout, the commands and the rules that break the app if ignored (Ractor-shareable blocks, everything loaded before boot). Each module appends a section with the same headings: Where, Main calls, Test, Pitfalls, Examples. SETUP.md is for getting the app running once, and AGENTS.md is the reference for working on it. `monk add` prints what it created, appended and skipped by module, the values to set before production, and at most three next steps. With `--json` it prints the same as one object, with file roles, example locations, the external services each next step needs and how to check them, and exit codes that tell success (0) from a usage error (1), a missing choice (2) and a conflict (3). Without a terminal, `monk` never prompts: a missing choice is an error naming the option to pass.

## Considered Options

- **Keep the flags, with a cleaner internal structure** (rejected: the rules between flags stay, and a module still can't be added to an existing app)
- **Only an interactive `monk new` that asks which modules to add** (rejected as the structure: it's a front end, and changes nothing about how modules combine or whether one can be added later; it stays possible on top of `--with`)
- **A demo for every module, in the user's files** (rejected: demos in `app/app.rb` or replacing `index.erb` can't be added to an existing app, and removing one meant editing several files; most modules are better shown by a commented example and proved by a test)
- **Working example routes instead of commented ones** (rejected: a live `/auth/request` without a rate limit lets anyone send mail to any address, and a live download route has no access check)
- **`monk check` instead of a generated test as each module's proof** (not taken: a test stays in the app, runs on every change and gives an exit code; checking a deployed environment is a separate roadmap item)
- **Routes added at an anchor before `App`'s closing `end`** (rejected: an anchor in a file the user owns, the thing this decision removes)
- **Redis only as a transport option of `live`** (rejected: an app may need Redis without sockets)
- **A manifest (`monk.yml`) listing the modules** (rejected: the installed modules are their config files, and a manifest would be a second record that could drift)
- **Keeping the old flags as aliases for one version** (rejected: pre-1.0, one app built from the scaffold, and the error shows the exact new command)
- **`monk scaffold` or `monk generate` as the command name** (not taken: in Rails "scaffold" means a CRUD resource, and `generate` is left for app code such as models and migrations)
